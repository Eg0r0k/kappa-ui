## Usage

```vue
<script setup lang="ts">
import { Button } from '@/components/ui/button'
import {
  Dialog,
  DialogBody,
  DialogClose,
  DialogContent,
  DialogDescription,
  DialogFooter,
  DialogHeader,
  DialogTitle,
  DialogTrigger,
} from '@/components/ui/dialog'
</script>

<template>
  <Dialog>
    <DialogTrigger as-child>
      <Button>Edit profile</Button>
    </DialogTrigger>
    <DialogContent>
      <DialogHeader>
        <DialogTitle>Edit profile</DialogTitle>
        <DialogDescription>Changes are saved when you press Save.</DialogDescription>
      </DialogHeader>
      <DialogBody>
        <!-- the content -->
      </DialogBody>
      <DialogFooter>
        <DialogClose as-child>
          <Button>Save</Button>
        </DialogClose>
      </DialogFooter>
    </DialogContent>
  </Dialog>
</template>
```

`Dialog` holds the state, `DialogTrigger` opens it, and `DialogContent` is the window. It renders the overlay, centres the window on the screen, and puts a close button in its top corner. Inside the window, `DialogHeader`, `DialogBody` and `DialogFooter` lay out the three parts. `DialogClose` around any button makes it close the dialog. `v-model:open` on `Dialog` opens it from code.

To put a form in the dialog, wrap the parts inside `DialogContent` in `<form class="contents">`, so the header, body and footer stay flex items of the window and the body still scrolls.

Underneath is Reka UI's dialog. Focus moves into the window and stays there. Escape or a press outside closes it, and focus returns to the trigger. The page behind is [shut](/docs/getting-started/overlays). The close button comes last in the window, so a form's first field takes focus when the dialog opens.

The window is as tall as its content, up to the height of the screen less 1rem on each side. Past that the body scrolls while the header and footer stay put. The body is a plain element with `overflow-y: auto`, so the dialog needs no scroll area.

### Scroll area

For kappa-ui's [scroll area](/docs/components/scroll-area) instead of the native scrollbar, give the window a height and let the scroll area take the rest with `min-h-0 flex-1`. A scroll area has no height of its own, so the window's height must not depend on it.

### Scrolling overlay

With `DialogScrollContent` in place of `DialogContent`, the window keeps its full height and the overlay scrolls instead, like a page. Use it for long reading, where a fixed header and footer would take too much room. It needs `modal`, which is on by default: without it the overlay renders nothing, so the window does not render either.

::component-preview{name="dialog-scroll-overlay"}
::

### Fullscreen

The window's position and size are classes, so `class` can make it fill the screen: `inset-0 size-full max-h-none max-w-none translate-none rounded-none border-0`. The classes they replace are merged away.

::component-preview{name="dialog-fullscreen"}
::

### Not dismissible

`DialogContent` passes on Reka UI's events. Prevent `escape-key-down` and `interact-outside`, and only a button in the window closes it. `:show-close-button="false"` removes the close button.

::component-preview{name="dialog-dismissible"}
::

### Nested

A dialog can open another from inside it. The new one stacks on top, and only the top one dims the page: the overlay below turns clear until the top dialog closes. Escape and outside presses close only the top one. When it closes, focus returns to the first dialog. Below, the inner dialog confirms a change with a `DialogClose` button, and the first dialog stays open and shows the result.

::component-preview{name="dialog-nested"}
::

### Custom layout

The parts are plain elements with classes, so any of them can be restyled or left out. This confirmation centres its header and drops the close button.

::component-preview{name="dialog-custom"}

## From code

A dialog can also open from code — a store, a router guard, a callback — without a place in any template, and hand back how it closed.

### Setup

Install the service once, next to the app:

```ts
// main.ts
import { createApp } from 'vue'

import { createDialogs } from '@/components/ui/dialog'
import App from './App.vue'

createApp(App).use(createDialogs()).mount('#app')
```

In Nuxt, do the same from a plugin:

```ts
// plugins/dialogs.ts
import { createDialogs } from '@/components/ui/dialog'

export default defineNuxtPlugin((nuxtApp) => {
  nuxtApp.vueApp.use(createDialogs())
})
```

Put one `DialogHost` in the root component. Dialogs opened from code render inside it, so they see everything the app provides above it, such as the router, i18n and stores:

```vue
<!-- App.vue -->
<script setup lang="ts">
import { DialogHost } from '@/components/ui/dialog'
</script>

<template>
  <RouterView />
  <DialogHost />
</template>
```

### Opening a dialog

A dialog opened from code is a component that renders `DialogContent`, the same parts as in a template. `useDialogContext()` gives it `close(value)` and `dismiss()`:

```vue
<!-- DeleteFileDialog.vue -->
<script setup lang="ts">
import { Button } from '@/components/ui/button'
import {
  DialogContent,
  DialogDescription,
  DialogFooter,
  DialogHeader,
  DialogTitle,
  useDialogContext,
} from '@/components/ui/dialog'

const props = defineProps<{ name: string }>()

const { close, dismiss } = useDialogContext()
</script>

<template>
  <DialogContent class="max-w-sm">
    <DialogHeader>
      <DialogTitle>Delete {{ props.name }}?</DialogTitle>
      <DialogDescription>The file moves to the bin for 30 days.</DialogDescription>
    </DialogHeader>
    <DialogFooter>
      <Button variant="outline" color="neutral" @click="dismiss()">Cancel</Button>
      <Button color="destructive" @click="close()">Delete</Button>
    </DialogFooter>
  </DialogContent>
</template>
```

`openDialog(component, props)` opens it and returns a promise of the result. The promise never rejects: `result.ok` is `true`, with `result.value`, after `close(value)`, and `false`, with `result.reason`, after anything else.

::component-preview{name="dialog-programmatic"}
::

| Reason | The dialog closed because |
|---|---|
| `escape` | Escape was pressed. |
| `outside` | A press or focus landed outside the window. |
| `swipe` | A swipe closed a drawer opened with `openDrawer` or `defineDrawer`. |
| `close-button` | A `DialogClose` was pressed, such as the close button. |
| `programmatic` | `dismiss()` was called. |
| `close-all` | `closeAllDialogs()` was called. |
| `unmount` | The `DialogHost` unmounted. |
| `no-host` | Nothing could show it: no service was installed or no `DialogHost` was mounted. The promise resolves at once and the console warns. |
| `error` | It failed to render. The error also reaches `app.config.errorHandler`. |

The promise is also a handle. `isOpen` is a ref, `close(value)` and `dismiss()` close the dialog from outside, and `patch(props)` changes the props given and keeps the rest. Only the first way of closing counts; later calls do nothing.

### One dialog, many calls

`defineDialog(component, { props })` fixes a component and its default props. Each `open(props)` starts from the defaults plus the props given. While the dialog is open, `open()` returns the same handle instead of a second window, and the definition's `isOpen` and `dismiss()` reach it from anywhere. Below, the caller patches the progress while the dialog is open:

::component-preview{name="dialog-define"}
::

A dialog that closes with a value names its type on both sides: `useDialogContext<string>()` inside, `open<string>()` outside. Without it the type is `void`. `openDialog<string>(component, props)` works too, but once a type argument is written TypeScript stops inferring the component, so the props go unchecked; `defineDialog` checks both.

### Waiting for work

`loading` from `useDialogContext()` holds the dialog open: while it is `true`, Escape, outside presses and `DialogClose` do nothing, and only `close()` or `dismiss()` from code close it. Disable the buttons while the work runs, so a second press cannot start it again.

::component-preview{name="dialog-async"}
::

### Keeping state

With `keepMounted: true`, a defined dialog is hidden instead of removed when it closes, so its state and DOM survive until it opens again. Each open still gets a promise of its own.

::component-preview{name="dialog-keep-mounted"}
::

### Closing everything

`closeAllDialogs()` closes every open dialog with `close-all`. Dialogs stay open across navigation; to close them on every route change:

```ts
router.afterEach(() => closeAllDialogs())
```

## Accessibility

The dialog's name comes from its `DialogTitle` and its description from its `DialogDescription`. Always give it a title: without one, screen readers announce an unnamed dialog. To name a dialog without showing the title, wrap the title in `VisuallyHidden` from `reka-ui`. The description is optional. When either is missing, the window renders an empty hidden one in its place, so Reka UI does not warn in the console.

::keyboard-table
---
rows:
  - keys: Tab / Shift + Tab
    description: Moves to the next or previous control in the window, wrapping around inside it.
  - keys: Escape
    description: Closes the dialog and returns focus to the element that opened it. While an input method is composing text, Escape ends the composition instead.
---
::
