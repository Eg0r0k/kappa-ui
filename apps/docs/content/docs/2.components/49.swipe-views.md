## Usage

```vue
<script setup lang="ts">
import { ref } from 'vue'

import { SwipeView, SwipeViews } from '@/components/ui/swipe-views'

const page = ref('inbox')
</script>

<template>
  <SwipeViews v-model="page" class="h-80">
    <SwipeView value="inbox">…</SwipeView>
    <SwipeView value="sent">…</SwipeView>
    <SwipeView value="drafts">…</SwipeView>
  </SwipeViews>
</template>
```

`v-model` holds the `value` of the page in the frame, a string or a number. Drag a page and it follows the finger. Let go and it settles on the nearest page, or on the next one after a quick flick, so a short fast swipe pages as surely as a long slow one. A finger can catch a page mid-way and drag on from where it is. Mouse, pen and touch all drag; on a touch screen a vertical drag still scrolls. Setting the model from code moves the page with the same transition.

Every page stays mounted. Pages out of the frame are `inert`, out of the tab order and the accessibility tree until a swipe brings them in. Content that should render late can wait for the `active` slot prop of `SwipeView`. Each `SwipeView` must be a direct child of `SwipeViews`.

Pages lie in a row, and the frame is as tall as the tallest page. With the window as the scroller the pages would share one scroll position, so give the frame a height and each page its own [Scroll Area](/docs/components/scroll-area), as the demo does.

Swipe Views is not a carousel: there is no loop, no autoplay, and one page in the frame. For those, use Embla or CSS scroll snap.

## Examples

### With Tabs

Tabs and Swipe Views share one `v-model`. Wrap each `SwipeView` in Reka's `TabsContent` with `force-mount` and `as-child`: the page becomes the tab panel, with `role="tabpanel"` and `aria-labelledby`, and stays mounted for the swipe. The demo at the top is built this way.

```vue
<script setup lang="ts">
import { TabsContent } from 'reka-ui'
</script>

<template>
  <Tabs v-model="tab">
    <TabsList variant="line">
      <TabsTrigger value="chats">Chats</TabsTrigger>
      <TabsTrigger value="groups">Groups</TabsTrigger>
    </TabsList>
    <SwipeViews v-model="tab" class="h-72">
      <TabsContent value="chats" force-mount as-child>
        <SwipeView value="chats">…</SwipeView>
      </TabsContent>
      <TabsContent value="groups" force-mount as-child>
        <SwipeView value="groups">…</SwipeView>
      </TabsContent>
    </SwipeViews>
  </Tabs>
</template>
```

## Layouts and effects

Swipe Views moves nothing itself. It writes CSS variables, and the classes on the pages turn them into motion: by default each page translates by `--swipe-snap-offset`. Replace a page's `translate-x-*` and width with your own classes for another layout. Anything that reads the variables follows the finger and settles with the transition, with no script per frame.

::component-preview{name="swipe-views-sidebars"}
::

The example above is laid out the way Discord does it on a phone. The server avatars are not a page: they stay at the start and the channel list sits beside them. A swipe towards the end slides the channel list away and fades the server names in beside the avatars; a swipe the other way, or a tap on a channel, brings the conversation over everything:

```vue
<SwipeViews v-model="view" :rubberband="false">
  <ul class="absolute inset-y-0 start-0 w-16">…</ul>
  <SwipeView
    value="servers"
    class="absolute inset-y-0 start-16 w-[calc(100%-4rem)] translate-x-0 opacity-[clamp(0,1+var(--swipe-view-position),1)]"
  >…</SwipeView>
  <SwipeView
    value="channels"
    class="pointer-events-none absolute inset-y-0 start-0 z-1 translate-x-[max(0px,calc(var(--swipe-snap-offset)+var(--swipe-view-start)))] ps-16"
  >
    <div class="pointer-events-auto h-full">…</div>
  </SwipeView>
  <SwipeView
    value="chat"
    class="absolute inset-y-0 start-0 z-10 translate-x-[calc(var(--swipe-snap-offset)+var(--swipe-view-start))]"
  >…</SwipeView>
</SwipeViews>
```

A page's size along the axis is the distance to the next page. The server names are `4rem` narrower than the frame, which is exactly how far the channel list travels to clear them. The channel list's page spans the whole frame so that the next step is the conversation's width; its first `4rem` lets taps through to the avatars, and `max(0px, …)` keeps it in place once the conversation covers it. The last page aligns to the end of the frame, so a narrow last page leaves the one before it peeking in from the other side.

At the first and the last page a drag stretches past the edge and springs back. `:rubberband="false"` stops it there instead, as the example does, so the conversation never pulls away from the channel list beneath it.

A page out of the frame is `inert`, so a tap on a page peeking in reaches whatever lies beneath it. To go back on a tap, put a button over the peek.

`--swipe-view-position` is `-1` for the page just behind, `0` for the one in the frame and `1` for the one ahead, fractional in between, so `opacity-[calc(1-0.5*abs(var(--swipe-view-position)))]` fades the neighbours.

::css-vars
---
rows:
  - name: --swipe-snap-offset
    default: 0px
    description: On the frame and every page, how far the pages have moved, in px. Negative going forwards, mirrored in right-to-left.
  - name: --swipe-snap-position
    default: "0"
    description: On the frame and every page, the index of the page in the frame, fractional while moving.
  - name: --swipe-view-index
    default: "0"
    description: On a page, its index.
  - name: --swipe-view-start
    default: 0px
    description: On a page, where it starts along the row, in px; mirrored in right-to-left.
  - name: --swipe-view-position
    default: "0"
    description: On a page, its index minus the position, -1 behind, 0 in the frame, 1 ahead.
  - name: --swipe-snap-duration
    default: var(--transition-duration-medium-4)
    description: How long a page takes to settle. Set it with a class on the frame or an ancestor.
---
::

The variables stop at the page, so the rest of the page does not restyle on every frame. An element inside a page that needs one takes it with `[--swipe-snap-offset:inherit]`.

## Swipe areas

A page with sideways gestures of its own competes with the swipe. [Swipe Actions](/docs/components/swipe-actions) rows work inside a page as they are: a drag on a row moves the row, and a drag towards a side the row has no actions on moves the page. For anything else, such as a map or a slider, put `data-no-drag` on it.

When a page is made entirely of such rows, set `swipe-area-only`. The pages then move only from a `SwipeViewsSwipeArea`, a strip along an edge, the way iOS goes back from the edge of the screen. `side="start"` leads back to the previous page and `side="end"` on to the next; a strip with no page on its side is off and lets taps through.

::component-preview{name="swipe-views-swipe-area"}
::

A strip lies over the content, so taps on its 20px land on the strip and not on what is beneath. In Safari on iOS the start edge also belongs to the browser's back swipe.

## Building your own

`useSwipeSnap` is the mechanism under Swipe Views, exported from the same file, for anything else that snaps between points: a custom sheet, a gallery, a pager with its own markup. It takes the snap positions in px and an index ref, handles the drag, the release and the catch, and writes `--swipe-snap-offset`, `--swipe-snap-position`, `data-dragging` and `data-settling` on its element. Put the `swipe-snap` class on that element for the transition.

```ts
import { ref } from 'vue'

import { useSwipeSnap } from '@/components/ui/swipe-views'

const frame = ref<HTMLElement>()
const index = ref(0)

const { position, snapTo, attach } = useSwipeSnap(frame, {
  points: () => [0, 320, 640],
  active: index,
})
```

| Option | Description |
|---|---|
| `points` | Snap positions along the axis in px, ascending from 0. A ref or a getter works too. |
| `active` | A ref with the index of the active point; setting it settles there. |
| `axis` | `x` or `y`. `x` by default. |
| `rtl` | Mirrors the x axis: the variables flip, the indexes do not. |
| `enabled` | `false` turns the drag off. |
| `sequential` | One point per gesture. `true` by default. |
| `rubberband` | Let a drag stretch past the reachable points. `true` by default; `false` stops it hard. |
| `canStart(move)` | Return `false` to refuse a drag that starts on the element. |

It returns the `offset`, `position`, `dragging` and `settling` refs, `snapTo(index, { animate })`, and `attach(element, { canStart })`, which makes another element start the same drag, as `SwipeViewsSwipeArea` does. Call `attach` during setup.

### Data attributes

::data-slots
---
rows:
  - slot: swipe-views
    attributes: data-orientation, data-disabled, data-dragging, data-settling
    description: The frame. `data-dragging` is set while a finger moves the pages, `data-settling` while they settle after it.
  - slot: swipe-view
    attributes: data-state, data-orientation
    description: A page. `data-state` is `active` for the page in the frame and `inactive` otherwise.
  - slot: swipe-views-swipe-area
    attributes: data-side, data-orientation, data-disabled
    description: A strip that starts a swipe. `data-disabled` is set when there is no page on its side.
---
::

## Accessibility

Pages out of the frame are `inert` and become reachable as soon as a swipe brings them on screen. Swipe Views has no keyboard of its own: a swipe is hard to discover and impossible without a pointer, so drive the model from controls too, such as [Tabs](/docs/components/tabs), [Page Indicator](/docs/components/page-indicator) or buttons. With Tabs, the `TabsContent` pattern above gives each page the tab panel's semantics.
