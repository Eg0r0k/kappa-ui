## Usage

```vue
<script setup lang="ts">
import { Upload } from '@lucide/vue'
import {
  FileUpload,
  FileUploadDescription,
  FileUploadDropzone,
  FileUploadIcon,
  FileUploadItem,
  FileUploadItemDelete,
  FileUploadItemMetadata,
  FileUploadItemPreview,
  FileUploadList,
  FileUploadTitle,
  FileUploadTrigger,
  fileKey,
} from '@/components/ui/file-upload'

const photo = ref<File | null>(null)
</script>

<template>
  <FileUpload v-slot="{ files }" v-model="photo" accept="image/*">
    <FileUploadDropzone as-child>
      <FileUploadTrigger>
        <FileUploadIcon><Upload /></FileUploadIcon>
        <FileUploadTitle>Drop your image here</FileUploadTitle>
        <FileUploadDescription>PNG or JPG, up to 2 MB</FileUploadDescription>
      </FileUploadTrigger>
    </FileUploadDropzone>
    <FileUploadList>
      <FileUploadItem v-for="file in files" :key="fileKey(file)" :file="file">
        <FileUploadItemPreview />
        <FileUploadItemMetadata />
        <FileUploadItemDelete />
      </FileUploadItem>
    </FileUploadList>
  </FileUpload>
</template>
```

`v-model` is a `File`, or `null` once it's cleared. Add `multiple` and it's a `File[]` instead, `[]` when empty. Every change hands you a new value, so watchers and form libraries notice it. The default slot always gives you `files` as an array, so one list template fits both.

Three ways in: the trigger opens the file dialog, the dropzone takes drops, and Ctrl+V pastes while focus is inside. All three go through the same checks.

Give it a `name`, and the files submit with the form like a plain `<input type="file">`. The hidden input always holds exactly the files on screen, including the ones that were dropped or removed, so `FormData` and `required` never disagree with what the user sees. A form reset puts back the `default-value` files, or none.

### Anatomy

`FileUpload` holds the files and the checks; the other parts are where they show.

- `FileUploadTrigger` is the one way in from the keyboard: a real button that opens the dialog. Make it a [Button](/docs/components/button) with `as-child`.
- `FileUploadDropzone` takes drops, and a click on it opens the dialog too. It is never a tab stop of its own. With `as-child` on the trigger, the whole zone is one button, as above. Put a trigger inside it instead to get a zone with a Browse button.
- `FileUploadIcon`, `FileUploadTitle` and `FileUploadDescription` fill the zone. Inside the trigger, the title is the button's name and the description its description.
- `FileUploadList` shows the files as rows or tiles, and nothing while there are none. Each `FileUploadItem` takes a `file`; key it with `fileKey(file)`, since two files can share a name. `FileUploadItemPreview`, `FileUploadItemMetadata` and `FileUploadItemDelete` read the file from their item.
- `FileUploadClear` removes every file.

## Examples

### Multiple

With `multiple`, new files join the list instead of replacing the old one. A file that is already there, same name, size and date, is turned away as a `duplicate`.

### Rejected files

`accept`, `max-size` and `max-files` keep files out of the model. The dialog's own filter is only a hint: the user can pick "All files", and a drop or a paste ignores it. So the component checks every file itself. `accept` takes MIME types, `type/*` and `.ext`, the same list the input does.

Whatever doesn't get in comes back through `reject`, once per pick, drop or paste, as `{ file, reason }`. The reason is `type`, `size`, `count`, `duplicate` or `directory` (a folder dropped in). Say why, or the user is left wondering where their file went.

::component-preview{name="file-upload-rejections"}
::

### Button

Leave the dropzone out and the trigger is all there is: an `as-child` Button, with the files listed under it. For a photo picker, show the picked image in the Button with `urlOf` from the default slot and put your own Remove on its corner.

::component-preview{name="file-upload-button"}
::

### Layouts

`layout="list"` on `FileUploadList` shows each file as a row with a name and a size; `grid` as a tile with its picture. Tiles without a picture keep their name, since a grid of identical document icons tells nobody anything.

The list goes wherever you put it: after the zone, or inside it, where it is part of the drop target.

### Variants

The dropzone's frame comes `outline` (dashed), `soft` (filled) or `subtle` (both).

### Sizes

`size` on the root, `xs` to `xl` on the [control scale](/docs/getting-started/sizing). The icon circle is a control's height, the glyph a control's icon, and the zone's padding, the list rows and the Remove buttons scale with them. The zone is as tall as its content; give it a `min-h-*` class for a taller one.

### Field

Inside a [Field](/docs/components/field) the trigger takes the field's `id`, so clicking the label opens the dialog. It also takes the description, the error and the field's invalid, disabled and required state. Press Apply without a file.

::component-preview{name="file-upload-field"}
::

### Form validation

Bind `v-model` to a Formisch field and let a Valibot schema check the files: `v.file()` for one, `v.array(v.file())` for many, with `v.mimeType()` and `v.maxSize()`. A schema error on one file has a path like `['floorPlans', 1]`; show it in that file's `FileUploadItemMetadata`. Formisch focuses the first invalid field on submit, so pass it the element the trigger rendered: put the ref on `FileUploadTrigger`, or on the `FileUploadDropzone` that is the trigger through `as-child`.

The built-in checks run first. Leave `max-size` off if the schema should own that message.

::component-preview{name="file-upload-form"}
::

### Upload progress

The component never uploads anything; it holds files. To upload as soon as files arrive, watch the model, start an upload for each new file, and draw its progress in `FileUploadItemMetadata`. Removing a file is the cancel button.

::component-preview{name="file-upload-progress"}
::

### Existing files

The model holds `File`s only, so a photo that's already on the server can't go in it. Show it yourself while the model is empty. Here a frameless dropzone holds an [Avatar](/docs/components/avatar), a Change trigger and a Remove button; a drop on the avatar counts, and the avatar rings while a file is dragged over it.

::component-preview{name="file-upload-avatar"}
::

### Browse button

A dropzone that holds its content and an `as-child` trigger: the zone takes drops and clicks, the Browse button takes focus. `FileUploadClear` makes the Remove all button.

::component-preview{name="file-upload-custom"}
::

### Drop anywhere

A drop outside a dropzone opens the file in the browser, and the component doesn't touch the page to stop that. For a page-wide drop, listen on `window` yourself, call `preventDefault` on `dragover` and `drop`, and hand the files to the exposed `addFiles`, which runs the same checks.

::component-preview{name="file-upload-page-drop"}
::

## Known limits

- Files only. A file already on the server can't sit in the model; see [Existing files](#existing-files). Nuxt UI is working out a shape for this in [nuxt/ui#6927](https://github.com/nuxt/ui/pull/6927); widening the model later won't break yours.
- Nothing is announced when files are added, removed or rejected, and the Remove label is English. Use `reject` and a `role="status"` region as in [Rejected files](#rejected-files), and your own button calling `removeFile` for another language.
- `required` reaches assistive tech only through the label and the browser's own message: `aria-required` isn't allowed on a button.
- `open()` works only straight from a click or a key press. After an `await` or a timer, the browser blocks the dialog without a word.
- Safari doesn't say what's being dragged until the drop, so a file that will be rejected looks welcome until then.
- Safari before 14.1 can't put dropped files into the hidden input. `v-model` still works; native form submission misses them.
- Long lists aren't virtualized. File lists rarely run past a few dozen.

## Accessibility

The trigger is a real `<button type="button">`, so it never submits a form, and Enter and Space work without any key handling of ours. The dropzone is not a tab stop: inside it, a trigger is, so keyboard users get one stop per component, not two. The list, its Remove buttons and the hidden input sit outside the trigger, because anything interactive inside a button disappears for screen readers.

The description is read once, as the trigger's description, not again as part of its name.

Each Remove button is labelled "Remove" and the file name. After a removal, focus moves to the next file's Remove button, then the previous one, then the trigger, so removing several files in a row is a few presses of Enter.

The hidden input is `aria-hidden` and out of the tab order. When a `required` upload is empty, the browser focuses it to show its message; the dropzone shows that focus, and Tab moves on to the trigger.
