Colour tokens keep shadcn's names and are written in OKLCH. Every fill comes with a foreground meant to sit on it. In dark mode the fills turn light and their foregrounds dark, so `--primary` works both as a button fill and as link text on the page, in either theme.

Success, warning and info are the exception. A green, amber or sky blue dark enough to carry white text turns olive, brown and navy, so in light mode their fills stay bright under dark text, and text on the page uses `--success-text`, `--warning-text` and `--info-text` instead: `text-warning-text`, not `text-warning`.

Components read these tokens but do not set them: any shadcn theme works. The values below are kappa-ui's own, from the `theme` item described in [Installation](/docs/getting-started/installation#theme). They are read from this page, so the theme toggle changes them too.

Each card also lists the WCAG contrast of its pairs, measured as rendered in the theme shown: text needs 4.5:1, and control borders 3:1. A ratio between 3:1 and 4.5:1 is only enough for large text. The [Themes](/themes) page runs the same checks while you edit a theme, including the status colours.

## Brand colour

`--primary` and `--ring` are derived from `--brand`, which contributes only its hue and chroma. The lightness is fixed per theme — 0.48 in light, 0.78 in dark — and that is what keeps white on `--primary` above 4.5:1 whatever hue you pick. To rebrand, change one value:

```css
:root {
  --brand: oklch(0.6 0.2 150);
}
```

The [Themes](/themes) page builds this CSS for you: pick a colour, a neutral, a radius and a font, or roll random ones, and copy the result.

The derivation uses relative colour syntax: Chrome 119, Safari 18, Firefox 128 and later. Older browsers fall back to the static values in `:root` and `.dark`, which match the default blue, not your brand. If you support them, update those static values as well.

`--brand` is read where `--primary` is declared, on `:root` and `.dark`. Setting `--brand` on an element further down changes nothing unless you redeclare the derived tokens on the same selector.

## Tones

A component with a `color` prop is drawn in a tone. `color="success"` sets `data-color="success"` on its root, and a rule in `@kappa-ui/core/tailwind.css` turns that into the variables every variant reads. Three are inputs; the other four are derived from them and can be overridden.

| Variable                | Value                                     | Role                                                                                |
| ----------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------- |
| `--tone`                | input                                     | The fill of the `solid` variant.                                                    |
| `--tone-foreground`     | input                                     | Text and icons on that fill.                                                        |
| `--tone-text`           | input                                     | Text in this colour on the page: `outline`, `ghost`, `link`, and the toast icon.    |
| `--tone-soft`           | 12% of `--tone` over transparent          | The fill of `soft` and `subtle`.                                                    |
| `--tone-soft-foreground` | `--tone-text`                            | Text on the soft fill.                                                              |
| `--tone-border`         | `--tone-text`                             | The edge of `outline`.                                                              |
| `--tone-border-subtle`  | 25% of `--tone-border` over transparent   | The edge of `subtle`.                                                               |

The built-in tones read the tokens above: `primary` and `destructive` are their pair, with the fill doubling as the text colour; `success`, `warning` and `info` write their text in `--success-text`, `--warning-text` and `--info-text`; `neutral` fills with `--foreground`, softens with `--secondary` and draws its edges in `--input`.

Switch, Checkbox, Radio and Slider have no `color` prop. They take the `tone-control` utility from `@kappa-ui/core/tailwind.css`: the `primary` tone, with `--input` as the edge while unchecked. `tone-invalid` turns the tone, the edge and the halo `destructive`, under the variant that marks the control invalid: `aria-invalid:` on the control, `in-aria-invalid:` inside an invalid group, `has-[[aria-invalid=true]]:` around the slider's thumbs. To draw one in another tone, set the inputs in its `class`, such as `class="[--tone:var(--success)] [--tone-foreground:var(--success-foreground)]"`.

A tone of your own is three tokens and one rule. Declare the tokens per theme next to the rest of your theme, then map them:

```css
:root {
  --pro: var(--color-violet-600);
  --pro-foreground: var(--color-violet-50);
  --pro-text: var(--color-violet-700);
}
.dark {
  --pro: var(--color-violet-400);
  --pro-foreground: var(--color-violet-950);
  --pro-text: var(--color-violet-300);
}

[data-slot][data-color='pro'] {
  --tone: var(--pro);
  --tone-foreground: var(--pro-foreground);
  --tone-text: var(--pro-text);
}
```

```vue
<Button color="pro">Upgrade</Button>
<Badge color="pro" variant="soft">Pro</Badge>
<Alert color="pro" variant="subtle">Your trial ends in 3 days.</Alert>
```

Keep `[data-slot]` in the selector: the derived values are set on `[data-slot][data-color]`, and a rule with lower specificity could not override one. To override one, add it to the same rule, for example `--tone-soft: var(--color-violet-50)` when the design has its own tint.

A scale of 50 to 950, from Tailwind or from a design file, maps like this:

|                     | Light       | Dark |
| ------------------- | ----------- | ---- |
| `--tone`            | 600         | 400  |
| `--tone-foreground` | white or 50 | 950  |
| `--tone-text`       | 700         | 300  |

Your own elements can join in: give one `data-slot` and `data-color`, and `bg-tone-soft`, `text-tone-text` and the other `tone-*` colours work as classes on it and its children. A one-off colour without a rule is a class on the component itself: `class="[--tone:var(--color-pink-500)] [--tone-foreground:white] [--tone-text:var(--color-pink-700)]"`.

## States and shape

Buttons show hover and press as a translucent layer of their own text colour, drawn by the `state-layer` utility, rather than as a separate hover colour per variant. A disabled button takes its colours from `--foreground` whatever its variant. The [ripple](/docs/utilities/ripple) uses the same pressed opacity, and while one is attached, the state layer leaves the press to it.

Keyboard focus is the `focus-ring` utility on every component: a 3px outline in `--ring` at half strength, outside the element, or inside it with `focus-ring-inset`. Being an outline, it leaves the element's own shadow alone and stays visible in forced-colours mode. Use it the same way in your own components: `focus-visible:focus-ring`.

Corners grow with height. Controls 28px tall take `--radius-md`, 32 to 40px `--radius-lg`, and 48px or more `--radius-xl`; badges under 24px take `--radius-sm`. Parts that sit inside a container, like menu items, tabs and the buttons of an input group, take the container's radius less their distance from its edge instead, so the corners stay concentric.

  - name: --state-selected

    description: Opacity of the primary tint under a selected option, list item or choice card.
  - name: --disabled-opacity
    default: 38%
    description: Opacity of `--foreground` for disabled text and icons.
  - name: --disabled-container-opacity
    default: 12%
    description: Opacity of `--foreground` for disabled fills and outlines.
  - name: --scrim
    default: oklch(0 0 0 / 40%)

  - name: --surface-border
    default: var(--border)

  - name: --radius
    default: 0.75rem
